# David AI — Frontend Prompts, Plans, and Rebuild Record

This package consolidates the available David AI frontend prompt files you supplied, the planning and architecture records created from those directives, capability matrices, validation records, and Command Center implementation documents. It is intended as a detailed source package for reviewing the David AI frontend direction or briefing a future implementation team.

## Reading order

Begin with the material in `01-user-supplied-prompts/`. These are the available original directive, roadmap, capability, frontend-review, and pasted prompt files from the active workspace. Then read the architecture in `02-plans-and-architecture/`, followed by the objective capability and validation records in `03-capability-and-validation/`. The connected Command Center history is retained in `04-command-center-records/` because the Agent Nexus and Command Center were designed as one David AI platform.

| Folder | Contents | Purpose |
|---|---|---|
| `01-user-supplied-prompts` | Original available frontend, command-center, capability, readiness, roadmap, and pasted directive files | Source requirements and planning input |
| `02-plans-and-architecture` | Frontend replacement architecture, elite architecture, final frontend replacement report, and Fabric readiness record | Coherent implementation design and constraints |
| `03-capability-and-validation` | Capability matrix, attachment validation, frontend validation, and preview report | Truthful delivered capability and test evidence |
| `04-command-center-records` | Command Center implementation, capability, gap-analysis, and browser-review records | Shared-platform history and integration context |

## Package boundaries

The package excludes application source code, media recordings, uploaded voice models, database contents, user data, build artifacts, browser logs, environment files, and API credentials. These exclusions keep the archive portable and safe to share while retaining the frontend planning detail you requested.

> The documents describe both implemented behavior and planned or external-provider-dependent behavior. Use the capability matrices and validation reports to distinguish verified functionality from requirements that still depend on a configured provider, worker, or physical-device test.
